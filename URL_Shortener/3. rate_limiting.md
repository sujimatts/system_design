## What is Rate Limiting?

Rate limiting **controls how many requests a client can make to a server within a defined time window**. It acts as a traffic cop — protecting services from abuse, overload, and cascading failures.

---

## Real-World Usage

| Scenario | Limit Example |
|---|---|
| GitHub API | 5,000 req/hour per authenticated user |
| Twitter/X API | 300 tweets/3 hours |
| Login brute-force protection | 5 failed attempts → 15 min lockout |
| DDoS mitigation | Drop IPs exceeding N req/sec |
| LLM APIs (OpenAI) | Tokens per minute (TPM) limits |

---

## Algorithms

### 1. Token Bucket ⭐ (Most Common)

- A bucket holds N tokens. This bucket holds the maximum capacity, for example, 1M tokens. On top of that, you can also define token limits per user or IP address.
- Tokens refill at a fixed rate (e.g., 10/sec).
- Used by: AWS, Stripe, most API gateways.

### 2. Leaky Bucket

- Requests enter a queue (bucket). Processed at a **fixed outflow rate**.
- Excess requests overflow (dropped).
- **Smooths traffic** — no burst allowed.
- Used by: network traffic shaping, older CDNs.

```
Requests in ──▶ [Queue] ──▶ drip at fixed rate ──▶ Server
                  │
              overflow → drop
```

### 3. Fixed Window Counter

- Divide time into fixed windows (e.g., 1-min slots). Count requests per window.
- Simple but has a **boundary spike problem**: 100 req at 00:59 + 100 req at 01:01 = 200 req in 2 seconds despite a "100/min" limit.

```
|--- window 1 ---|--- window 2 ---|
  t=0         t=60             t=120
```

### 4. Sliding Window Log

- Store timestamp of each request. Count requests in the last N seconds.
- **Accurate** — no boundary spike. Memory-intensive (store all timestamps).

### 5. Sliding Window Counter ⭐ (Best Balance)

- Hybrid: uses fixed window counts + weighted overlap from previous window.

- **Accurate + memory efficient**. Used by: Cloudflare, Redis-based limiters.

**Example** (limit = 100 req/min, you are at t = 1:45):

```
|--- prev (0:00–1:00) ---|--- current (1:00–2:00) ---|
      prev_count = 80          curr_count = 30
                                      ▲ t=1:45 (45s elapsed, 25% of prev window remains)

80 × 25% = 20   (fading old requests)
20 + 30  = 50   ✅ under 100 → allow, 50 more remaining
```

The moment count hits 100 → **429 blocked**. Just wait — old requests keep fading, count drops below 100, and you are allowed in again automatically. No hard reset, just a smooth continuous slide.

---

## Algorithm Comparison

| Algorithm | Memory | Burst | Accuracy | Complexity |
|---|---|---|---|---|
| Token Bucket | Low | Yes | High | Medium |
| Leaky Bucket | Low | No | High | Medium |
| Fixed Window | Very Low | Yes (boundary) | Low | Low |
| Sliding Window Log | High | No | Exact | High |
| Sliding Window Counter | Low | Partial | High | Medium |

## System Design: Distributed Rate Limiter

### Architecture

```
                        ┌─────────────────────────────────────────┐
                        │            API Gateway / LB              │
                        └────────────┬────────────────────────────┘
                                     │
                   ┌─────────────────▼──────────────────┐
                   │         Rate Limiter Service         │
                   │                                      │
                   │  ┌──────────────────────────────┐   │
                   │  │    Rule Engine                │   │
                   │  │  (per user / IP / API key)   │   │
                   │  └──────────────┬───────────────┘   │
                   │                 │                    │
                   │  ┌──────────────▼───────────────┐   │
                   │  │    Redis Cluster             │   │
                   │  │  (counters + TTL)            │   │
                   │  │                              │   │
                   │  │  KEY: rate:{userId}:{window} │   │
                   │  │  VAL: count (INCR + EXPIRE)  │   │
                   │  └──────────────────────────────┘   │
                   └──────────┬─────────────┬────────────┘
                              │             │
                    ┌─────────▼──┐     ┌────▼──────┐
                    │ Allow ──▶  │     │ Reject    │
                    │ Backend    │     │ 429 + header│
                    └────────────┘     └────────────┘

Response Headers:
  X-RateLimit-Limit: 1000
  X-RateLimit-Remaining: 42
  X-RateLimit-Reset: 1716393600
  Retry-After: 30
```

### Key Components

| Component | Role |
|---|---|
| **API Gateway** | First point of enforcement (per route/method) |
| **Rate Limiter Service** | Stateless workers; fetch rules + check counters |
| **Redis** | Shared, atomic counter store (INCR + EXPIRE) |
| **Rule Engine** | Defines limits per: user tier, IP, API key, endpoint |
| **Config Store** | Dynamic rule updates without redeployment |



## How to Configure a Rate Limiter

```
STEP 1 ── Where to enforce?
┌──────────────────┐   ┌───────────────────┐   ┌────────────────────┐
│  API Gateway     │   │   Middleware       │   │  Standalone Svc    │
│  Kong/AWS/APIM   │   │   Express/FastAPI  │   │  Centralised       │
│  Config only ✅  │   │   Per-service      │   │  Cross-service     │
└────────┬─────────┘   └─────────┬──────────┘   └──────────┬─────────┘
         └─────────────────────┬─┘────────────────────────── ┘
                               │
                               ▼
STEP 2 ── Rule Engine  (Config Store — hot reload, no redeploy)
┌─────────────────────────────────────────────────────────────────┐
│  user:free  →  100/min       user:pro  →  10,000/min           │
│  ip         →  200/min       endpoint:/search  →  10/min       │
│                                                                 │
│  First match wins. Multiple rules → all buckets checked.       │
│  If any bucket exhausted → 429.                                │
└──────────────────────────────┬──────────────────────────────────┘
                               │
                               ▼
STEP 3 ── Redis  (atomic INCR + TTL auto-expiry)
┌─────────────────────────────────────────────────────────────────┐
│  rate:user:u123:{window}   → INCR   (TTL = window size)        │
│  rate:ip:1.2.3.4:{window}  → INCR   (TTL = window size)        │
└───────────────┬─────────────────────────────┬───────────────────┘
                │                             │
           under limit                    over limit
                │                             │
                ▼                             ▼
STEP 4 ── Allow                   STEP 5 ── Reject
┌──────────────────────┐          ┌──────────────────────────────┐
│  Forward to Backend  │          │  HTTP/1.1 429                │
│                      │          │  X-RateLimit-Limit: 100      │
│                      │          │  X-RateLimit-Remaining: 0    │
│                      │          │  Retry-After: 30             │
└──────────────────────┘          └──────────────────────────────┘
```

## Where to Enforce?

```
Client ──▶ [CDN/Edge] ──▶ [API Gateway] ──▶ [Middleware] ──▶ [Service]
              L1                L2               L3              L4
           (IP-based)      (API key)         (user tier)    (business logic)
```

- **Edge/CDN (L1):** Coarse IP-level DDoS protection (Cloudflare, AWS Shield)
- **API Gateway (L2):** Per-API-key / per-route limits (Kong, APIM, AWS API GW)
- **Middleware (L3):** Per-user / per-tenant limits inside the app
- **Service level (L4):** Fine-grained resource limits (DB queries, LLM tokens)

Multi-layer is preferred — each layer stops a different threat class.


**Clarify:**
- What are we rate limiting? (user, IP, API key, tenant)
- What window? (per second, minute, hour)
- Hard reject or queue?
- Distributed or single-node?
- Acceptable accuracy vs. memory tradeoff?

**Default answer for most scenarios:**
> Sliding Window Counter + Redis (INCR + EXPIRE) + API Gateway enforcement + 429 with Retry-After header.
