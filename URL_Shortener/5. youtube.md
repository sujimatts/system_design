# System Design: Designing YouTube (Video Streaming Service)

## 1. Core Components & Stack

| Component | Selected Technology | Role in Architecture |
| :--- | :--- | :--- |
| **API Gateway** | Envoy / Kong | Handles routing, SSL termination, authentication, and client-facing rate limiting. |
| **Raw Blob Storage** | Amazon S3 / Google Cloud Storage | Durable storage for original, uncompressed user video uploads. |
| **Message Queue** | Apache Kafka | Decouples video uploads from the heavy, asynchronous transcoding process. |
| **Transcoding Engine** | Custom worker cluster (FFmpeg) | Chunks, encodes, and compresses videos into multiple resolutions and streaming formats. |
| **Transcoded Blob Storage** | Amazon S3 (Optimized storage) | Stores the final, segmented video chunks (.ts/.m4s files) and index manifests (.m3u8/.mpd). |
| **CDN (Content Delivery Network)** | Cloudflare / Akamai | Caches transcoded video chunks close to geographical user hubs to eliminate latency. |
| **Metadata Database** | MongoDB / Cassandra | Handles write-scaling for video metadata (title, description, tags, uploader ID). |
| **Distributed Cache** | Redis | Caches hot video metadata and acts as a write-buffer for dynamic metrics. |

## 2. Thought Process & Configurations

### A. Upload vs. Playback Decoupling
*   **The Problem:** Uploading is a write-heavy, highly stateful process (long-running HTTP connections, heavy payload). Streaming is a read-heavy, low-latency process (small chunk requests).
*   **Configuration:** Separate into two dedicated, horizontally-scaled microservices:
    *   **Upload Service:** Scaled based on active TCP connections. Configured with a reverse proxy that supports large timeouts and chunked upload requests.
    *   **Playback Service:** Completely stateless, scaled based on high Requests Per Second (RPS), placed behind a strict read-cache tier.

### B. Video Chunking & Adaptive Bitrate Streaming (ABR)
*   **The Problem:** Storing and streaming a single massive 2GB video file is highly inefficient. If the user's connection drops for a second, the video buffers or restarts.
*   **Configuration:** 
    1.  **Chunking:** The original video is chopped into discrete **2 to 5-second segments**.
    2.  **Transcoding:** Each segment is transcoded into multiple resolutions (144p, 360p, 720p, 1080p, 4K) using standard codecs (H.264 for universal playback, VP9/AV1 for viral videos to save bandwidth).
    3.  **Manifest File:** A Master Playlist file (`.m3u8` for Apple HLS or `.mpd` for MPEG-DASH) is generated. It maps resolutions to the paths of individual video chunk files.
    4.  **Client-Side Playback:** The client player continuously checks the user’s real-time bandwidth and fetches the corresponding chunk quality from the manifest.

### C. Scaling the View Counter (The Hotkey Write Problem)
*   **The Problem:** If a video goes viral, millions of viewers trigger simultaneous write operations to update the view counter, locking the Database and causing system failure.
*   **Configuration:** 
    *   Never update the database synchronously.
    *   **Redis Buffer:** Playback client fires a lightweight view event to a cache cluster. The view counter is incremented in memory using atomic operations: `INCR video:<id>:views`.
    *   **Batch Writer:** A background cron service polls Redis and flushes the aggregated view updates to the persistent Metadata DB in batch updates (e.g., every 10 seconds or 10,000 views).

## 3. End-to-End Flow

### The Upload Flow (Asynchronous Pipeline)
1.  **Initiate:** Client requests a session URL from the API Gateway and begins uploading raw video in **5MB chunks** to the **Upload Service**.
2.  **Save Raw:** The Upload Service streams chunks into the **Raw Blob Storage**.
3.  **Notify Queue:** Once upload is complete, the Upload Service writes an event to **Kafka** (`video_id`, `raw_s3_url`).
4.  **Transcode:** **Transcoding Workers** consume the event from Kafka:
    *   They pull the raw video file.
    *   Split the video into chunks.
    *   Encode chunks in parallel using FFmpeg into different qualities.
    *   Write the processed segments and the master `.m3u8` manifest to **Transcoded Blob Storage**.
5.  **Write Metadata:** Workers update the **Metadata Database** marking the video status as `Active` and saving the manifest URL.

### The Playback Flow (Low-Latency Cache-First)
1.  **Fetch Manifest:** Client requests metadata and the streaming manifest URL for `video_id` via the **Playback Service**.
2.  **Read Cache:** Playback Service checks **Redis**. If it's a cache miss, it reads from the **Metadata DB** and populates Redis.
3.  **Return Manifest:** The master `.m3u8` file is returned to the client.
4.  **Fetch Video:** The client player reads the manifest and requests the first 3-second video chunk (e.g., `chunk_001_1080p.ts`) from the nearest **CDN Edge Node**.
5.  **Edge serving:** 
    *   *Cache Hit:* The CDN returns the cached chunk in milliseconds.
    *   *Cache Miss:* The CDN pulls the chunk from the **Transcoded Blob Storage**, caches it locally, and serves it to the viewer.

```text
[VIDEO UPLOAD PATHWAY]
Uploader Client 
      │
      ▼ (1. Resumable Upload Chunks)
  API Gateway 
      │
      ▼ (2. Stream Chunks)
 Upload Service ──────> Raw Blob Storage [S3] (3. Write Raw Original)
      │
      ▼ (4. Publish Task)
 Kafka Event Queue 
      │
      ▼ (5. Consume Task)
Transcoding Workers 
      │
      ├──────> Transcoded Storage [S3] (6. Save Resolution Chunks & Manifest)
      │
      └──────> Metadata Database (7. Mark Video Active & Link Manifest)


[VIDEO PLAYBACK PATHWAY]
Viewer Client ──────> Playback Service 
                             │
                             ├─────> Redis Cache (A. Fast Metadata Lookup)
                             │          │
                             │          ▼ (B. Fallback on Cache Miss)
                             │       Metadata DB
                             │
                             ▼ (C. Return .m3u8 Playback Manifest)
Viewer Client <──────────────┘
      │
      ▼ (D. Request 3-second Segment)
CDN Edge Cache ──────> (Cache Hit: Return segment instantly) ──────> Viewer Client
      │
      └─(Cache Miss)─> Fetch from Transcoded Storage [S3] ──> Cache & Serve
```
